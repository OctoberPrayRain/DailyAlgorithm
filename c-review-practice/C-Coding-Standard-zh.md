## 1. 命名

---

### 让命名贴切

命名是编程的核心。古人相信知道一个人的真名就能掌控那个人。如果你能为一个事物想出贴切的名字，你就为自己和后来者赋予了掌控代码的力量。别笑！

命名是对其所处生态系统的长期深度思考的结果。只有理解整个系统的程序员才能创造出"契合"系统的名字。如果名字恰当，一切都会自然融洽：关系清晰、意义可推导、按常理推断也能如预期工作。

如果你发现所有名字都可以叫 `Thing` 和 `DoIt`，那你可能该重新审视设计了。

---

### 函数命名

- 通常每个函数都执行一个动作，因此名字应清楚表明它做什么：用 `check_for_errors()` 而不是 `error_check()`，用 `dump_data_to_file()` 而不是 `data_file()`。这样也能更好地区分函数和数据对象。

  结构体通常是名词。通过让函数名使用动词并遵循其他命名规范，程序可以更自然地阅读。

- 后缀有时很有用：
  - `_max` — 表示某事物的最大值。
  - `_cnt` — 表示当前计数。
  - `_key` — 键值。

  例如：`retry_max` 表示最大重试次数，`retry_cnt` 表示当前重试次数。

- 前缀有时很有用：
  - `is_` — 用于询问某事。任何人看到 `Is` 就知道这是一个问题。
  - `get_` — 获取一个值。
  - `set_` — 设置一个值。

  例如：`is_hit_retry_limit`。

---

### 包含单位

如果变量表示时间、重量或其他单位，应在命名中包含单位，以便开发者更容易发现问题。例如：

```c
uint32 timeout_msecs;
uint32 my_weight_lbs;
```

---

### 结构体命名

- 使用下划线（`_`）分隔命名组成部分。
- 在结构体中声明变量时，按用途组织声明顺序，以尽量减少因编译器对齐问题导致的内存浪费，然后按大小排序，最后按字母顺序排序。例如，不要写成 `int a; char *b; int c; char *d;`，而应写成 `int a; int b; char *c; char *d;`。每个变量单独占一行并有自己的类型，不过在声明位域（bitfield）时可以例外（以明确它们是同一个位域的一部分）。注意，一般情况下不鼓励使用位域。主要结构体应声明在使用它们的文件的顶部，如果在多个源文件中使用，则应放在单独的头文件中。结构体的使用应通过独立声明，如果在头文件中声明，则应使用 `extern`。为每个成员名使用有意义的前缀可能很有帮助，例如对于 `struct softc`，前缀可以是 `sc_`。

#### 示例

```c
struct foo {
    struct foo *next;       /* 活跃的 foo 列表 */
    struct mumble amumble;  /* mumble 的注释 */
    int bar;
    unsigned int baz:1,     /* 位域；如果需要可对齐条目 */
                 fuz:5,
                 zap:2;
    uint8_t flag;
};
struct foo *foohead;        /* 全局 foo 列表的头 */
```

---

### 栈上变量命名

- 全部使用小写字母。
- 使用 `_` 作为单词分隔符。

#### 理由

- 通过这种方式，变量的作用域在代码中一目了然。
- 所有变量看起来都不同，在代码中易于识别。

#### 示例

```c
int handle_error(int error_number) {
    int            error = OsErr();
    Time           time_of_error;
    ErrorProcessor error_processor;
}
```

---

### 指针变量

- 将 `*` 靠近变量名，而非指针类型。

#### 示例

```c
char *name = NULL;

char *name, address;
```

---

### 全局变量

- 全局变量应加 `g_` 前缀。
- 应尽可能避免使用全局变量。

#### 理由

- 了解变量的作用域很重要。

#### 示例

```c
Logger  g_log;
Logger *g_plog;
```

---

### 全局常量

- 全局常量应全部大写，并使用 `_` 分隔。

#### 理由

这是全局常量命名的传统方式。你必须小心不要与其他全局 `#define` 和枚举标签冲突。

#### 示例

```c
const int A_GLOBAL_CONSTANT = 5;
```

---

### #define 与宏命名

- `#define` 和宏应全部大写，使用 `_` 分隔。宏应大写、加括号，并避免副作用。宏名前后的空格可以是任意空白字符，但整个文件中制表符的使用应保持一致。如果宏是函数的内联展开，函数名全部小写，宏使用相同的名字但全部大写。如果宏是一个表达式，将表达式用括号括起来。如果宏包含多条语句，使用 `do { ... } while (0)`，这样末尾的分号才能正常工作。将反斜杠右对齐，这样更易读。

#### 理由

这非常清楚地表明该值不可更改；对于宏而言，也能清楚表明你正在使用一个需要小心对待的结构。

宏名称和枚举标签使用相同名称时，可能会发生一些微妙的错误。

#### 示例

```c
#define MAX(a, b) blah
#define IS_ERR(err) blah
#define MACRO(v, w, x, y)                                               \
do {                                                                    \
    v = (x) + (y);                                                      \
    w = (y) + 2;                                                        \
} while (0)
```

---

### 枚举命名

#### 标签全部大写，使用 `_` 分隔单词

这是枚举标签的标准规则。最后一个元素不加逗号。

#### 示例

```c
enum PinStateType {
    PIN_OFF,
    PIN_ON
};
```

#### 为错误状态设置标签

能够表明一个枚举不处于任何有效状态通常很有用。为未初始化或错误状态设置一个标签。如果可能，将其设为第一个标签。

#### 示例

```c
enum { STATE_ERR, STATE_OPEN, STATE_RUNNING, STATE_DYING };
```

## 2. 格式化

---

### 大括号策略

三种主要的大括号放置策略中，推荐以下一种：

```c
if (condition) {        while (condition) {
    ...                     ...
}                       }
```

---

### 何时需要大括号

所有 `if`、`while` 和 `do` 语句要么必须有大括号，要么必须写在一行内。

#### 始终使用大括号的形式

所有 `if`、`while` 和 `do` 语句都需要大括号，即使其中只有一条语句。例如：

```c
if (1 == somevalue) {
    somevalue = 2;
}
```

##### 理由

这能确保以后有人添加代码行时，大括号已经存在，不会忘记添加。它提供了更一致的外观。这不会影响执行速度。而且很容易做到。

#### 单行形式

```c
if (1 == somevalue) somevalue = 2;
```

##### 理由

它在添加新行时提供安全保障，同时保持紧凑可读的格式。

---

### 为闭合大括号添加注释

为闭合大括号添加注释有助于阅读代码，因为你不需要找到开始的大括号就能知道它在关闭什么。

```c
while (1) {
    if (valid) {

    } /* if valid */
    else {
    } /* not valid */

} /* end forever */
```

---

### 考虑屏幕尺寸限制

有些人喜欢让代码块适配常见的屏幕尺寸，这样阅读代码时就不需要滚动。

---

### 关键字与函数的括号策略

- 不要在关键字旁边放括号。关键字和括号之间应加空格。
- 要在函数名旁边放括号。
- 不要在 `return` 语句中使用不必要的括号。

#### 理由

- 关键字不是函数。通过在关键字旁边放括号，会让关键字和函数名看起来一样。

#### 示例

```c
if (condition) {
}

while (condition) {
}

strcpy(s, s1);

return 1;
```

---

### 行长度限制

- 一行不应超过 78 个字符。

#### 理由

- 即使有了大显示器我们把窗口拉得很宽，但打印机只能打印那么宽。而且我们仍然需要打印代码。
- 窗口越宽，屏幕上能放的窗口就越少。更多的窗口比更宽的窗口更好。
- 我们甚至可以在所有终端和打印机上正确查看和打印 diff 输出。

---

### If Then Else 格式化

#### 布局

由程序员决定。不同的大括号风格会产生稍微不同的外观。一种常见的方法是：

```c
if (condition) {
} else if (condition) {
} else {
}
```

如果你有 `else if` 语句，通常最好始终保留一个 `else` 块，以便发现未处理的情况。即使没有采取纠正措施，也可以在 `else` 中放一条日志消息。

#### 条件格式

始终将常量放在等式/不等式比较的左侧。例如：

```c
if (6 == errorNum) ...
```

一个原因是，如果你漏掉了一个 `=`，编译器会帮你发现错误。第二个原因是，它把你要找的值放在最前面，你能直接看到，而不是埋藏在表达式的末尾。适应这种格式需要一点时间，但之后真的很有用。

---

### switch 格式化

- 允许从一个 `case` 语句落入下一个 `case` 语句，但必须包含注释。
- `default` 情况应始终存在，如果它不应该被到达但实际被到达了，应触发错误。
- 如果需要创建变量，将所有代码放在一个块中。

#### 示例

```c
switch (...)
{
    case 1:
        ...
    /* 注释 */

    case 2:
    {
        int v;
        ...
    }
    break;

    default:
}
```

---

### goto、continue、break 与 ?: 的使用

#### goto

`goto` 语句应谨慎使用，正如在任何结构良好的代码中一样。关于 `goto` 的争论很无聊，这里不展开。它们主要的有用之处是跳出多层嵌套的 `switch`、`for` 和 `while`，尽管需要这样做可能表明内部结构应该被拆分成单独的函数，并返回成功/失败的状态码。

```c
for (...) {
    while (...) {
        ...
        if (disaster) {
            goto error;
        }
    }
}
...
error:
    clean up the mess
```

当必须使用 `goto` 时，伴随的标签应单独占一行，并位于后续代码的左侧。`goto` 应被注释说明（可能在块头中），解释其用途和效用。

#### continue 与 break

`continue` 和 `break` 实际上是伪装的 `goto`，所以在这里一并讨论。

`continue` 和 `break` 像 `goto` 一样应谨慎使用，因为它们在代码中像魔法一样。一个简单的咒语就能把读者传送到某个通常没有文档说明的地方。

`continue` 的两个主要问题是：

- 它可能绕过测试条件。
- 它可能绕过递增/递减表达式。

考虑以下两个问题的示例：

```c
while (TRUE) {
    ...
    /* 大量代码 */
    ...
    if (/* 某个条件 */) {
        continue;
    }
    ...
    /* 大量代码 */
    ...
    if (i++ > STOP_VALUE) break;
}
```

注意："大量代码"是必要的，这样程序员才不会轻易发现问题。

从上面的例子可以得出进一步的规则：在同一个循环中混合使用 `continue` 和 `break` 绝对是灾难的温床。

#### ?:

问题在于人们通常试图在 `?` 和 `:` 之间塞入太多代码。以下是几条清晰性规则：

- 将条件放在括号中，以便与其他代码区分开来。
- 如果可能，测试对应的动作应该是简单的函数。
- 将 then 和 else 对应的动作放在单独的行上，除非可以清楚地放在一行内。

#### 示例

```c
(condition) ? funct1() : func2();

// 或者

(condition)
    ? long statement
    : another long statement;
```

---

### 一行一条语句

除非语句之间关联非常紧密，否则每行只应有一条语句。

理由：

1. 代码更易读。也使用一些空白。没有什么比阅读一行接一行没有空白或注释的代码更糟糕的了。

#### 每行一个变量

与此相关的是，始终每行只定义一个变量：

**不要这样：**
```c
char **a, *x;
```

**要这样：**
```c
char **a = 0;  /* 添加文档 */
char  *x = 0;  /* 添加文档 */
```

理由：

1. 可以在该行上为变量添加文档。
2. 清楚地表明变量已初始化。
3. 声明清晰，减少了想声明 `char` 却意外声明了指针的概率。

## 3. 文档

---

### 注释应讲述故事

将你的注释视为描述系统的故事。期望你的注释能被机器人提取并形成手册页。类注释是故事的一部分，方法签名注释是另一部分，方法参数又是一部分，方法实现也是一部分。所有这些部分应该编织在一起，在另一个时间点向其他人准确地告知你做了什么以及为什么这么做。

---

### 记录决策

注释应记录决策。在每一个你有选择做什么的点上，放置一条注释，描述你做了哪个选择以及为什么。考古学家会发现这是最有用的信息。

---

### 使用文档头

使用像 [Doxygen](http://www.doxygen.org) 这样的文档提取系统。

这些文档头的结构化方式使其可以被解析和提取。它们不像普通注释那样无用。所以花点时间把它们填好。如果你一次做对了，可能就不需要更多的文档了。

---

### 注释布局

项目的每个部分都有特定的注释布局。[Doxygen](http://www.doxygen.org) 有推荐的注释布局格式。

---

### 让陷阱明确

对超出正常控制流而改变的变量，或其他可能在维护期间出问题的代码，明确添加注释。嵌入式关键字用于指出问题和潜在问题。考虑一个机器人会解析你的注释，寻找关键字，将它们剥离出来，并生成报告，以便人们在需要时可以特别关注。

#### Gotcha 关键字

- **`@author:`** 指定模块的作者
- **`@version:`** 指定模块的版本
- **`@param:`** 指定函数的参数
- **`@return:`** 指定函数的返回值
- **`@deprecated:`** 表明某函数不再使用
- **`@see:`** 在文档中创建链接，指向应查阅的文件/函数/变量，以获得对当前代码块更好的理解
- **`@todo:`** 说明还有什么待完成
- **`@bug:`** 报告在代码片段中发现的 bug

#### Gotcha 格式

- 让 gotcha 关键字成为注释中的第一个符号。
- 注释可以由多行组成，但第一行应是自包含的、有意义的摘要。
- 评论者的姓名和备注日期应包含在注释中。这些信息虽然也在源代码仓库中，但要找出它是何时以及由谁添加的，可能需要相当长的时间。通常 gotcha 存在的时间比它们应该存在的更长。嵌入日期信息可以让其他程序员做出这个决定。嵌入作者信息让我们知道该问谁。

---

### 函数声明注释

函数头应放在声明它们的文件中。这意味着大多数函数的头会在 `.h` 文件中。然而，像 `main()` 这样在 `.h` 文件中没有显式原型声明的函数，头应放在 `.c` 文件中。

---

### 包含语句文档

包含语句应添加文档，告诉用户为什么包含了特定文件。

```c
/*
 * 内核头文件放在最前面。
 */
/* 非本地头文件用尖括号。 */
/*
 * 如果是网络程序，接下来放网络头文件。
 * 按子目录对头文件分组。
 */
/*
 * 然后空一行，接着是 /usr 头文件。
 * /usr 头文件应该排序！
 */
```

## 4. 复杂度管理

---

### 分层

分层是降低系统复杂度的主要技术。系统应被划分为多个层。层之间应通过定义良好的接口与相邻层通信。当一层使用非相邻层时，就发生了分层违规。

分层违规简单地意味着层之间存在未通过定义良好的接口控制的依赖关系。当某一层发生变化时，代码可能会崩溃。我们不希望代码崩溃，因此我们希望层只与其他相邻层工作。

有时为了性能原因我们需要跨层。这没问题，但我们应该知道自己在做什么，并适当地添加文档。

## 5. 其他

---

### 一般建议

本节包含一些杂项的该做和不该做。

- 不要在需要离散值的地方使用浮点变量。将浮点数用作循环计数器是搬起石头砸自己的脚的好方法。始终将浮点数作为 `<=` 或 `>=` 来测试，永远不要使用精确比较（`==` 或 `!=`）。

- 编译器有 bug。常见的麻烦点包括结构体赋值和位域。你通常无法预测编译器有哪些 bug。你可以编写一个程序来避免所有已知在所有编译器上 broken 的结构。但你将无法编写任何有用的东西，你仍可能遇到 bug，而且编译器可能会在期间被修复。因此，只有当你被迫使用某个有 bug 的编译器时，才应该"绕过"编译器 bug 编写代码。

- 不要依赖自动美化工具。良好程序风格的主要受益者是程序员自己，尤其是在手写算法或伪代码的早期设计阶段。自动美化工具只能应用于完整的、语法正确的程序，因此在最需要关注空白和缩进的时候无法使用。程序员可以更好地完成函数或文件的完整视觉布局，这要归功于细心程序员对细节的正常关注（换句话说，部分视觉布局是由意图而非语法决定的，美化工具无法读心）。粗心的程序员应该学会成为细心的程序员，而不是依赖美化工具让他们的代码可读。最后，由于美化工具是必须要解析源代码的非平凡程序，复杂的美化工具不值得它带来的好处。美化工具最适合对机器生成的代码进行粗略格式化。

- 逻辑比较的第二个 `"="` 被意外遗漏是一个问题。以下写法令人困惑且容易出错。

  ```c
  if (abool = bbool) { ... }
  ```

  程序员真的是想在这里赋值吗？通常是的，但通常也不是。解决方案就是不要这样做，一种逆向的耐克哲学。相反，使用显式测试，避免带有隐式测试的赋值。推荐的形式是在测试之前先赋值：

  ```c
  abool = bbool;
  if (abool) { ... }
  ```

- 现代编译器会自动将变量放入寄存器。谨慎使用 `register` 来标识你认为最关键的那些变量。在极端情况下，将 2-4 个最关键的值标记为 `register`，其余标记为 `REGISTER`。后者可以在寄存器较多的机器上 `#define` 为 `register`。

### 正确使用 const

C 提供了 `const` 关键字，允许将不能更改的对象作为参数传递，以表明方法不会修改其对象。在正确的所有地方使用 `const` 被称为 "const 正确性"。一开始很难，但使用 `const` 真的能让你的编码风格更严谨。Const 正确性会与你共同成长。

---

### 使用 #if 而非 #ifdef

使用 `#if MACRO` 而不是 `#ifdef MACRO`。有人可能会这样写代码：

```c
#ifdef DEBUG
    temporary_debugger_break();
#endif
```

另一个人可能会用关闭的调试信息来编译代码：

```bash
cc -c lurker.cc -DDEBUG=0
```

总是使用 `#if`，如果你必须使用预处理器的话。这样即使 `DEBUG` 完全没有定义也能正常工作：

```c
#if DEBUG
    temporary_debugger_break();
#endif
```

如果你真的需要测试一个符号是否已定义，使用 `defined()` 结构来测试，这样你以后可以向条件中添加更多内容，而无需编辑程序中已有的文本：

```c
#if !defined(USER_NAME)
 #define USER_NAME "john smith"
#endif
```

---

### 注释掉大段代码

有时为了测试，需要注释掉大段代码。

#### 使用 #if 0

最简单的方法是使用 `#if 0` 块：

```c
void
example()
{
    great looking code

    #if 0
    lots of code
    #endif

    more code
}
```

你不能使用 `/**/` 风格的注释，因为注释不能包含注释，而你的大段代码中肯定会包含注释，不是吗？

不要使用 `#ifdef`，因为有人可能会在编译器命令行上无意中触发 ifdefs。`#if 0` 的问题是，即使几天后，你或任何人都不知道这段代码为什么被注释掉。是因为某个功能被取消了？还是因为它有 bug？它编译不过？它可以被加回来吗？这是个谜。

#### 使用描述性的宏名替代 #if 0

```c
#if NOT_YET_IMPLEMENTED
#if OBSOLETE
#if TEMP_DISABLED
```

#### 添加注释说明原因

添加一条简短的注释，解释为什么它未实现、已过时或被临时禁用。

### C 文件扩展名

简而言之：头文件使用 `.h` 扩展名，源文件使用 `.c` 扩展名。

---

### 头文件中不要定义数据

不要在头文件中放置数据定义。例如：

```c
/*
 * aheader.h
 */
int x = 0;
```

1. 通过无辜地使用头文件来静默插入消耗空间的代码是糟糕的魔法。
2. 在头文件中定义变量不是常见做法，所以当出现问题时，开发者不会想到去头文件中查找。
3. 考虑在 `.c` 文件中定义一次变量，并使用 `extern` 语句来引用它。

### C 与 C++ 混合

为了与愚蠢的链接器向后兼容，C++ 的链接时类型安全性是通过在链接符号中编码类型信息来实现的，这个过程称为**名字修饰（name mangling）**。这在链接到 C 代码时会产生问题，因为 C 函数名不会被修饰。当从 C++ 调用 C 函数时，函数名会被修饰，除非你关闭它。名字修饰通过 `extern "C"` 语法来关闭。如果你想在 C++ 中创建 C 函数，必须用上述语法包装它。如果你想从 C++ 调用 C 库中的 C 函数，你也必须用上述语法包装。以下是一些示例：

#### 从 C++ 调用 C 函数

```c
extern "C" int strncpy(...);
extern "C" int my_great_function();
extern "C"
{
    int strncpy(...);
    int my_great_function();
};
```

#### 在 C++ 中创建 C 函数

```c
extern "C" void
a_c_function_in_cplusplus(int a)
{
}
```

#### __cplusplus 预处理器指令

如果你有必须在 C 和 C++ 环境中编译的代码，那么你必须使用 `__cplusplus` 预处理器指令。例如：

```c
#ifdef __cplusplus
extern "C" some_function();
#else
extern some_function();
#endif
```

### 初始化所有变量

- 你必须始终初始化变量。始终。每次。带有 `-W` 标志的 gcc 可能会捕获对未初始化变量的操作，但也可能不会。

#### 理由

- 比你想象的更多的问题最终都可以追溯到未初始化的指针或变量。

---

### 短函数

- 函数应限制在单页代码以内。

#### 理由

- 思想是每个方法代表实现单个目标的技术。
- 大多数关于效率的论点从长远来看都是错误的。
- 真正的函数调用确实比不调用慢，但这需要一个深思熟虑的决定（参见过早优化）。

### 记录空语句

始终为空 `for` 或 `while` 语句的空体添加文档注释，以明确空体是有意的，而不是遗漏了代码。

```c
while (*dest++ = *src++)
{
    ;
}
```

### 不要默认将 if 测试为非零

不要默认测试非零，即：

```c
if (FAIL != f())
```

比

```c
if (f())
```

更好，即使 `FAIL` 的值可能是 0，而 C 认为 0 是假。显式测试会在以后有人决定将失败返回值从 0 改为 -1 时帮助你。即使比较值永远不会改变，也应使用显式比较；例如，应写 `if ((bufsize % sizeof(int)) == 0)` 而不是 `if (!(bufsize % sizeof(int)))`，以反映测试的数字（而非布尔）性质。一个常见的麻烦点是使用 `strcmp` 来测试字符串相等性，其结果**永远永远**不应被默认。首选方法是定义一个宏 `STREQ`：

```c
#define STREQ(a, b) (strcmp((a), (b)) == 0)
```

或者更好，使用内联方法：

```c
inline bool
string_equal(char *a, char *b)
{
    return (strcmp(a, b) == 0);
}
```

注意，这只是一个示例，你真的应该使用标准库的字符串类型来进行比较。

非零测试通常可以为满足以下限制条件的谓词和其他函数或表达式默认使用：

- 返回 0 表示假，其他什么都不返回。
- 命名使得（比如说）**true** 返回的含义绝对明显。将谓词命名为 `is_valid()`，而不是 `check_valid()`。

### 通常避免嵌入式赋值

嵌入式赋值语句有其适用的时间和地点。在某些结构中，如果不让代码变得更臃肿和更难读，就没有更好的方式来实现结果。

```c
while (EOF != (c = getchar())) {
    process the character
}
```

`++` 和 `--` 运算符算作赋值语句。同样，具有副作用的函数也是如此。在人为的地方使用嵌入式赋值语句来提高运行时性能也是可能的。然而，应该考虑在人工位置使用嵌入式赋值时增加的速度与降低的可维护性之间的权衡。例如：

```c
a = b + c;
d = a + r;
```

不应替换为

```c
d = (a = b + c) + r;
```

即使后者可能节省一个周期。从长远来看，随着优化器的成熟，两者之间的时间差异会减少，而随着人类对后者代码中发生事情的记忆开始消退，维护性方面的差异会增加。

---

### 使用枚举还是不使用枚举

C 允许常量变量，这应该使枚举作为常量的用法过时。不幸的是，在大多数编译器中常量会占用空间。有些编译器会移除常量，但不是全部。常量占用空间使得它们不能在像嵌入式系统这样的紧凑内存环境中使用。工作站用户应该使用常量并忽略本讨论的其余部分。

一般来说，枚举优于 `#define`，因为枚举能被调试器理解。

要注意枚举的大小不保证。所以如果你有一个可以取已知范围的值的类型，并且它通过消息传输，你不能使用枚举作为该类型。使用正确的整数大小，并使用常量或 `#define`。在整数和枚举之间转换非常容易出错，因为你可能会转换一个不在枚举中的值。

### 宏

#### 不要把 C 变成 Pascal

不要通过宏替换来改变语法。这会让除肇事者以外的所有人都无法理解程序。

#### 用内联函数替代宏

在 C 中，宏对于代码效率不是必需的。使用内联。然而，用于小函数的宏是可以的。

#### 示例

```c
#define MAX(x, y) (((x) > (y) ? (x) : (y))    // 获取最大值
```

上面的宏对于整数可以用以下内联函数替代，且不会损失效率：

```c
inline int
max(int x, int y)
{
    return (x > y ? x : y);
}
```

#### 小心副作用

宏应谨慎使用，因为当用具有副作用的表达式调用时，可能会产生错误。

#### 示例

```c
MAX(f(x), z++);
```

#### 始终将表达式用括号括起来

在宏中放置表达式时，始终将表达式用括号括起来，以避免潜在的交换律运算歧义。

#### 示例

```c
#define ADD(x, y) x + y
```

必须写成

```c
#define ADD(x, y) ((x) + (y))
```

#### 让宏名唯一

像全局变量一样，宏可能与其他包的宏冲突。

1. 用包名作为宏名的前缀。
2. 避免简单和常见的名字如 `MAX` 和 `MIN`。

### 不要魔法数字

魔法数字是源代码中赤裸裸的裸数字。它是魔法的，因为没有人知道它是什么意思，包括作者在内三个月后也不知道。例如：

```c
if      (22 == foo) { start_thermo_nuclear_war(); }
else if (19 == foo) { refund_lotso_money(); }
else if (16 == foo) { infinite_loop(); }
else                { cry_cause_im_lost(); }
```

在上面的例子中，22 和 19 是什么意思？如果数字变了或者数字本身就是错的，你怎么知道？不要用魔法数字，而是使用一个有实际意义的名字。你可以使用 `#define`、常量或枚举作为名字。用哪一个是设计选择。例如：

```c
#define   PRESIDENT_WENT_CRAZY  (22)
const int WE_GOOFED = 19;
enum {
    THEY_DIDNT_PAY = 16
};

if      (PRESIDENT_WENT_CRAZY == foo) { start_thermo_nuclear_war(); }
else if (WE_GOOFED            == foo) { refund_lotso_money(); }
else if (THEY_DIDNT_PAY       == foo) { infinite_loop(); }
else                                  { happy_days_i_know_why_im_here(); }
```

这不是更好吗？`const` 和 `enum` 选项更可取，因为在调试时，调试器有足够的信息来同时显示值和标签。`#define` 选项在调试器中只显示为一个数字，非常不便。`const` 选项的缺点是会分配内存。只有你知道这是否对你的应用重要。

### 错误返回检查策略

- 检查每个系统调用的错误返回，除非你知道你希望忽略错误。例如，`printf` 返回一个错误码，但你很少会检查它的返回值。如果你真的在意，可以将其返回值强制转换为 `(void)`。
- 为每个系统错误消息包含系统错误文本。
- 检查每次对 `malloc` 或 `realloc` 的调用，除非你知道你使用的这些调用版本做了正确的事情。你可能希望为这些调用（包括 `new`）提供自己的包装器，这样你就可以始终做正确的事情，开发者也不必到处做内存检查。
